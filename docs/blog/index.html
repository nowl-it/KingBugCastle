Reverse-engineering an Android game into a server it never expected

King God Castle is a Korean auto-battler with a single backend, a packed anti-cheat, and no offline mode. This is the story of turning it into a private server — told through what broke, what lied, and what finally worked.

I

The game you are not allowed to read

It starts with a spreadsheet problem. King God Castle stores its entire balance — every hero, every skill tier, every drop table, every localized string — in a bundle of XML files that the client downloads at login. That bundle is not shipped in the APK. It arrives over HTTP, in a binary container, and it is the difference between "I play this game" and "I understand this game."

So the first month was not programming. It was archaeology. Dump the bundle. Unpack the container. Line up Strings_EN_US.xml against Strings_VI.xml and discover that skill descriptions are templates assembled from three separate tables. Extract sprite atlases with UnityPy and find that hero portraits live in a dedicated illustration bundle while the same hero's battle sprites live in an atlas of nineteen 130×140 cells.

None of it is documented anywhere. Every fact is inferred, and every inference has to survive contact with the actual client. A useful habit forms in this phase: the client is the specification. If a field name is ambiguous, decompile the class that reads it. If a rule is unclear, find the constant. The XML tells you the shape of the data; only the binary tells you what the data means.

By June the shape was clear enough to try something stupid: stand up a fake server, point a patched client at it, and see how far the login screen gets.

II

The binary that isn't there

It got surprisingly far. FastAPI on port 8080, a hand-written table mapping the client's route names to response models, and a JSON file containing one plausible player. Login worked. The lobby loaded. Then every panel that needed real data threw a null reference because the response model was empty — which is how the project learned its first structural lesson: a route with no model answers an empty model, and an empty model crashes a panel.

Then the game updated to v171, and the ground moved. v171 ships no libil2cpp.so on disk. The file that contains all the game's compiled C# is packed and encrypted inside the anti-cheat library at runtime, unpacked into memory, and executed from there. Every tool in the standard toolkit expects a file. There wasn't one.

Unpacking it took a week of disassembly: find the loader, find the integrity checks, find the parser that rejects a bad header, and neutralise exactly enough of them that the packer hands you a plain ELF without noticing it has been robbed. The result is a clean libil2cpp.so plus the metadata, both matching the same build — and that matching part matters more than it sounds, because the metadata carries string literal indices that the compiled code has baked in. A version mismatch does not produce a warning. It produces gibberish. 

integrity bail-outs   bl ; tbnz w0,#31,<fail>   ×4
parser error returns  mov w8,#-1 ; str w8,[sp,#0x94] ; b   ×4

With the binary in hand, the SSL bypass is almost anticlimactic: three ValidateCertificate methods, each replaced with mov w0,#1 ; ret. Four bytes of honesty per method.

III

Convincing a client that already knows you're lying

A private server is not a reimplementation of a game. It is a performance. The client believes what you tell it, and every panel it draws is a demand for a specific shape of data at a specific moment.

The hard part is the invariants nobody wrote down. A deck array must be at least six elements, because the lobby indexes six fixed UI slots. It must also be at most six, because the deck editor loops over your array while indexing its own. Both bounds were confirmed by decompiling both functions. Guessing either one produced a crash that looked like a completely different bug.

The client does not validate your data. It indexes it. the single most expensive lesson of the project

Then there are the response fields with a vocabulary of their own. Reward types are not free-form: "Item" is not a valid type. The client compares against a fixed literal set — InventoryItem, Key, UnitSoulItem, Treasure_*, Skin, and a dozen more — and an unmatched string resolves to no icon at all. The reward still renders. It just renders with the wrong picture and a nonsense number, which is a much harder bug to notice than a crash.

By the end of July, every route the client can call had a real answer. Not a stub — an answer that makes the corresponding panel behave the way a player expects: shop stock, mission reward claiming, territory labour, Babel towers, colosseum seasons, attendance streaks, clan membership, cosmetics you own and equip, invasion first-clear rewards.

IV

Two people should be able to play

A server for one person is a toy. The moment a second device connects, everything that was implicitly "the save file" has to become "a save, keyed by an identity" — and identity is where this project produced its most interesting failures.

The first attempt was reasonable: if a login arrives with no id, fall back to the active save. That is correct for a single-player demo and catastrophic for a service. A client that loses its guest id — cache clear, reinstall, a factory reset — logs in over and over with no identity, and each time it is handed somebody else's world, with a session bound to it. The server log showed the same account logging in every few minutes for weeks. It looked like a stuck client. It was a stuck design.

"My account turned into a different player" is never a data-loss bug. It is an identity bug wearing a data-loss costume. after the third report of the same symptom

The second failure was subtler. Sign-in on Android goes through Google, and the client's native path expects the backend to hand back an access token. Our fake backend answered that endpoint with an empty model — no token. That was fine for as long as the device had a token from an earlier session. On a fresh install it wasn't: the login went out with no id, got refused, and every subsequent request served a throwaway template save. Three different users reported "the game reset my account." The account was never touched. The token was never minted.

Now an id-less login is refused in multiplayer. The template save's placeholder uid can never become a save key. A new guest identity gets a new save, and an old save can be re-attached deliberately. The rule is unglamorous and it holds: never guess an identity.

V

Free, or not at all

The hosting requirement was stated once and never negotiated: nothing may cost money. That single constraint shaped the architecture more than any technical preference.

The result is a free-tier ARM box running the API on 8080 and TLS on 8443, behind a CDN that handles certificates, with the domain split three ways — one hostname for the game client, one for the admin dashboard, one for the player portal. CI runs the full test suite on every push. A separate workflow builds the patched client and publishes it as a GitHub release, because release assets are free and object storage is not. The one genuinely large artifact — the stock 1.1 GB game package needed as build input — is downloaded from GitHub during the build and deleted immediately afterward, so it never touches the instance at all.

Deploys run through a key that can execute exactly one command. Not a shell with a restriction: a key whose authorized_keys line pins a command. If the hook is dirty, it refuses. If it's clean, it fast-forwards and restarts. There is no path from CI to a prompt. 

~/.ssh/authorized_keys
restrict,command="/home/ubuntu/kgc/server/deploy_hook.sh" ssh-ed25519 AAAA…

The trade-off is real: free tiers get tiny disks. One upgrade required swapping a boot volume between instances because the running one could not hold both the old and new artifacts at the same time. On a paid plan that's a resize. On a free plan it's an evening.

VI

The bugs that were not bugs

Some of the longest investigations ended with the conclusion "the code was doing exactly what it was told." Three of them are worth remembering because the pattern repeats.

The client logged in seventeen times per second. No exception, no error, no logcat entry — just requests. The lobby's update loop compares the current time against tomorrow, and if the day has turned, it re-fetches everything. Our save had tomorrow stored, frozen at account creation, so the day turned once and never stopped turning. The fix was three lines: derive it from the clock instead of storing it. The lesson is general — anything derived should never be persisted.

The game hung on "Loading resources." The HTTP request went out and the response arrived. The callback never ran. It turned out the game's own HTTP client had grown an analytics call inside it, and analytics initialization throws on a device without Google Play Services. The exception did not surface anywhere useful; it simply killed the completion handler mid-flight. Two functions stubbed to ret and the loading screen disappeared.

The binary was corrupt and we blamed the framework. A localised stack overflow on a loading screen was diagnosed twice as an inherent bug in the async runtime. It was actually twenty-one stray bytes in a hand-patched library — one of them a branch that had overwritten a constant inside a state machine, turning a linear coroutine into infinite recursion. The rule that came out of it is in the repository in bold: never hand-patch the library you ship. Regenerate it from pristine bytes and validate with a hash-like check that refuses to proceed if anything else moved.

Fabricating a plausible explanation is worse than saying "I don't know yet." One of them costs an hour; the other costs a week. written down after the fourth misdiagnosis
VII

A skin that does not exist

The best test of whether you actually understand a system is to make it display something that was never authored. Adding a new hero costume turned out to be a five-layer problem disguised as a data row.

Layer one is obvious: a row in the unit XML pointing at a sprite name. Layer two is the asset bundle — the bundle is content-addressed, and the client verifies its CRC against a catalog baked into the download. Custom bytes cannot produce the original CRC, and editing the catalog to lie about it corrupts the whole download. The solution is not to fake the checksum but to remove the check: four instruction patches at runtime so the catalog's CRC is simply not enforced.

Layer three is the sprite atlas. A hero's battle animation is nineteen frames in a fixed grid, and each frame carries tight polygon geometry computed for that specific silhouette. Reuse a wider image inside the old mesh and the frame is cropped and then zoomed — posed wrong, cut off, bleeding into the neighbouring cell. Every one of the nineteen frames has to be rebuilt with its own quad, texture rect, and pivot-derived UV transform. The verification is not "does the texture look right" but "does each sprite read back as exactly 130×140".

Layer four is the prefab: a clone of the source character with ten animation clips, an animator controller, and a unique render-data key. Share the source's render key and the cloned portrait silently resolves to the original — or to nothing.

Layer five is the addressables catalog, which needs five new locations: the texture and sprite for both the battle atlas and the illustration, plus the prefab. Get four of five right and the skin row appears in the shop, its thumbnail is blank, and its large portrait falls back to a default illustration.

When it finally worked, it worked completely — animation, portrait, thumbnail, shop entry, equip flow. Nothing in the game knows the character wasn't authored by the original studio.

VIII

What comes after the game

Once you can read the master data fluently, the game stops being the only interesting artifact. The data is.

That produced a strategy compendium: every build-defining strategy in the roguelike mode, what each one does, which ones are mutually exclusive, how the roll pool weights change as you take upgrades — and a simulator that takes your three visible options, your current tier, and the strategy you want, and tells you the odds. It is one static HTML file, bilingual, with no build step and no dependencies, published from the repository itself.

It produced a dashboard: player lookup, item and hero grants, mail with arbitrary text, an audit log, and a live view of API traffic. And a monitor that watches the official CDN and announces, in fifteen languages, when a new version or a new patch appears.

The project also produced this document, which is the honest version: the misdiagnoses, the shouting, the sessions that ended in "you're making things up again," and the ones that ended with a working lobby.
