# Deploy & Run

How to bring the server up, connect a device, and push a change to the client.

## Servers - game API, admin, and Player Dashboard

The client speaks HTTPS; the SSL-bypass patch in the client accepts any cert, so a self-signed
cert is fine. Run **both** listeners (HTTP for convenience/CDN, HTTPS for the real client):

```bash
cd server
uvicorn server:app --host 0.0.0.0 --port 8080                                   # HTTP
uvicorn server:app --host 0.0.0.0 --port 8443 --ssl-keyfile key.pem --ssl-certfile cert.pem  # TLS
```

- `cert.pem` / `key.pem` are generated by `setup.py` (gitignored - never ship the private key).
- Both processes cache `real_cdn/*` file bytes **at import** (`_CDN_FILES` in `server.py`). After a
  master-data/bundle change you **must restart both** to serve the new bytes.
- Player state (`state/players.db`) is **not** cached - `load_state()` reads the row per request.
  State edits are live without a restart.
- Dashboard: `python3 dashboard.py` → http://localhost:8081/ - the admin UI (players, heroes, items,
  accessories, mail, battle tracker, server logs/routes/CDN). `server/run.py` starts it alongside both
  game-server processes with `--reload`, which is the normal way to run all three in development.
  Its front end is a Next.js / React static export served from `webui-next/out`. To edit: modify
  `webui-next/src/`, run `pnpm run build` in `webui-next/`, and refresh the browser.
- Player Portal: its own FastAPI process serves the same static export on internal `:8082`
  (default public hostname: `https://player.kingbugcastle.id.vn/`). It has its own
  `kgc_player` cookie and `/portal/api/*` routes; it never accepts the admin dashboard cookie or
  a game `accesstoken`. Rebuild `webui-next` after changing either dashboard or portal UI, then
  restart `serve_playerportal.sh` if it is already running.
- Google rewarded video is deliberately disabled until a provider-verifiable server callback exists.
  The browser's `rewardedSlotGranted` event is forgeable and cannot mint tickets; configuring
  `GAM_REWARDED_AD_UNIT_PATH` currently returns a clear 503 instead of granting value.
- To exercise the in-game **Google login** button, start with `GLOGIN_DEV=1` (dev account picker, no
  Google Cloud project needed) or the real `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET`/`GLOGIN_PUBLIC_URL`;
  otherwise `/glogin` returns 503. `GLOGIN_DEV=1` hands out a session for any account id you name -
  never on a public server. See [multi-account-login.md](multi-account-login.md).
- `/admin` on `:8080` is **not** a UI - it redirects to the dashboard. Its `/admin/api/*` routes are
  live and the dashboard proxies them (and creates new saves through them).

### Public Player Dashboard (`:8082`)

The three services have separate authority and hostnames:

| Public hostname | Internal service | Role |
|---|---:|---|
| `kingbugcastle.id.vn` | `8080` | game client API |
| `admin.kingbugcastle.id.vn` | `8081` | administrator dashboard |
| `player.kingbugcastle.id.vn` | `8082` | Player Dashboard |

Start the portal separately after the static UI has been built:

```bash
cd server/webui-next && pnpm run build
cd ..
PLAYER_PORTAL_PUBLIC_URL=https://player.kingbugcastle.id.vn \
GAM_REWARDED_AD_UNIT_PATH=/NETWORK_CODE/kgc_player_rewarded \
./serve_playerportal.sh start
```

`8082` is the **internal** separation point. Cloudflare's normal orange-cloud proxy does not
proxy an arbitrary public port such as `8082` directly. Route the player hostname to local `8082`
with a hostname-aware reverse proxy (Caddy/Nginx) or a Cloudflare Tunnel; do not publish a DNS
record that asks browsers to visit `:8082`.

### Public hostname proxy (OCI deployment)

The public host uses Caddy on `80/443`, while the application processes stay on their internal
ports. The tracked service/configuration sources are
`systemd/caddy.service`, `systemd/kgc-public.Caddyfile`, and
`systemd/kgc-playerportal.service`. Caddy routes these hosts:

| Host | Upstream |
|---|---|
| `kingbugcastle.id.vn` | `https://127.0.0.1:8443` |
| `admin.kingbugcastle.id.vn` | `http://127.0.0.1:8081` |
| `player.kingbugcastle.id.vn` | `http://127.0.0.1:8082` |

It reuses the game's origin certificate; Cloudflare SSL/TLS encryption must therefore be
**Full**, not Flexible. In Cloudflare, create the proxied `player` DNS record pointing at the
same public origin as the other hosts. The portal service runs on that origin and shares the
live `server/state/players.db` with the game process; never point a local portal at a copied DB.

Player-portal configuration belongs in `/etc/kgc/playerportal.env` on the public host; both
systemd and `serve_playerportal.sh` load it. It must contain `GLOGIN_STATE_SECRET` when Google
sign-in is enabled. Keep `KGC_BIND_HOST=127.0.0.1` (the default) and set
`KGC_TRUST_PROXY=1` only when Caddy/Tunnel is the sole ingress. For example, set
`PLAYER_DONATE_INSTRUCTIONS` to the bank/MoMo instructions you want players to see; it is
intentionally blank until configured.

In Google Cloud Console, add both authorised redirect URIs to the existing **Web application** OAuth
client before testing Google login:

```text
https://kingbugcastle.id.vn/glogin/callback
https://player.kingbugcastle.id.vn/portal/api/auth/google/callback
```

The portal process only accepts the second callback and sets `kgc_player` only on the player
hostname. The game process keeps only `/glogin/*`, so neither cookies nor OAuth responses cross the
game/admin boundary.

### Restarting cleanly

Easiest: **`server/run.py`** opens a terminal UI for the core development stack: both game
listeners, the admin API, and Next.js. It owns each process group, shows live status and logs, and
stops only the processes it started. The public Player Dashboard remains separate; start it with
`./serve_playerportal.sh start` after building the static UI on the Linux production host.

macOS/Linux:

```bash
cd server
python3 run.py
ADB_SERIAL=127.0.0.1:5555 python3 run.py   # default: localhost:5556 (redroid)
KGC_DEV_BIND_HOST=0.0.0.0 python3 run.py   # explicit LAN opt-in
python3 run.py --check                     # validate without starting anything
```

Windows PowerShell:

```powershell
cd server
py run.py
$env:ADB_SERIAL = "127.0.0.1:5555"; py run.py
$env:KGC_DEV_BIND_HOST = "0.0.0.0"; py run.py
py run.py --check
```

Controls: `j`/`k` or arrows select a service, `Enter` starts/stops it, `a` starts all, `x` stops all,
`r` restarts all, `d` connects `$ADB_SERIAL`, installs `tcp:443→:8443` and `tcp:80→:8080` reverse
routes, and clears a stale global proxy. `q` stops the owned processes and exits.

On Linux, processes can also be launched by hand (background jobs die with the shell, so detach each):

```bash
pkill -f "uvicorn server:app"
cd server && setsid uvicorn server:app --host 0.0.0.0 --port 8080 \
  > /tmp/kgc_server.log 2>&1 < /dev/null & disown
cd server && setsid python3 -m uvicorn server:app --host 0.0.0.0 --port 8443 \
  --ssl-keyfile key.pem --ssl-certfile cert.pem > /tmp/kgc_server_tls.log 2>&1 < /dev/null & disown
ss -ltn | grep -E ':8080|:8443'      # confirm both listening
```

The TUI shows each resolved log path. They live under the platform temporary directory
(`/tmp` on Linux, typically `/var/folders/...` on macOS, and `%TEMP%` on Windows). The TLS log is
where you watch the real client's requests (`POST /auth/login`, `GET /player`, `[GAME/START] body=…`,
`CDN GET /patch/…`).

## Connect a device (uniform path - works on every target)

Bake `127.0.0.1` into the client and route the device's `:443` back to your `:8443` with `adb reverse`.
No root, no hosts-file edit, no privileged port. Identical on redroid / BlueStacks / LDPlayer / a real
USB phone - all support `adb reverse`.

| Target | adb connect | Typical serial |
|--------|-------------|----------------|
| redroid (Linux/Docker) | `adb connect localhost:5556` | `localhost:5556` |
| BlueStacks | enable ADB, `adb connect 127.0.0.1:5555` | `127.0.0.1:5555` |
| LDPlayer | `adb connect 127.0.0.1:5555` | `127.0.0.1:5555` |
| Real phone | USB debugging, plug in | from `adb devices` |

```bash
# 1. Build + install the side-by-side test app (com.nowl.castle, "King Bug Castle")
ADB_SERIAL=<serial> python3 server/rebuild_arm64_mod.py --host 127.0.0.1

# 2. Route :443 -> :8443 (re-run after replug / emulator restart - it is per-connection).
#    Press `d` in `server/run.py` to apply these routes again.
adb -s <serial> reverse tcp:443 tcp:8443
adb -s <serial> reverse tcp:80  tcp:8080     # optional (CDN is https, usually not needed)

# 3. Launch. The v170.1.00 mod build uses MainActivity; modern builds launch via
#    AirbridgeActivity instead (see docs/private-build.md).
adb -s <serial> shell am start -n com.nowl.castle/co.ab180.airbridge.unity.AirbridgeActivity
```

Healthy boot in logcat: `LibMainWrap → libxigncode.so → libmain_real.so → Unity il2cpp`, then
`Hooked BattleManager.Update` / `Hooked PostListItem.Set`. Then the TLS log fills with `200 OK`.

> Modern builds (v171/v172) use the unified builder
> (`server/builders/build_private.py`), `AirbridgeActivity`, and plain HTTP - see
> [private-build.md](private-build.md).

For **remote players** (no adb) you bake a public host instead - see [../SHARE.md](../SHARE.md).

## Push a master-data change to the client

Any edit under `server/xml_live/*.xml` (stage spawns, skins, text, `MinVersion`) reaches the client
only through the CDN xml bundle:

```bash
python3 server/builders/rebuild_xml_bundle.py    # rebuilds real_cdn/xml + updates AssetHash.txt
# restart BOTH uvicorns (see above) so they re-cache real_cdn/
adb -s <serial> shell "rm -rf /sdcard/Android/data/com.nowl.castle/files/UnityCache"   # optional
adb -s <serial> shell am force-stop com.nowl.castle
```

The `AssetHash.txt` for `xml` changes on every rebuild → the client's CDN check detects the diff and
re-downloads the bundle on next launch. Details: [cdn-master-data.md](cdn-master-data.md).

## Server-only state change

Editing a player row in `state/players.db` (dashboard, or `playerdb.load/save`) takes effect on the
client's **next fetch** of the relevant endpoint - no restart, no re-download. See [save-editing.md](save-editing.md).
